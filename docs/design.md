# 设计说明

## 处理对象

年度报告处理包含五个步骤：来源检索、正文识别、版本选择、文件检查和章节标题定位。项目将各步拆成独立模块，并使用显式数据结构传递结果。

本项目将流程拆为来源、分类、版本、文件和章节五层。各层输出显式数据结构，上层可以保留或改写下层判断。

## 模块结构

```text
DisclosureSource
      │
      ▼
Announcement
      │
      ├── 标题分类
      ▼
版本判断
      │
      ├── current
      ├── superseded
      ├── ambiguous
      └── not_candidate
      │
      ▼
PDF检查
      │
      ▼
章节标题候选
```

### 来源层

来源适配器只负责查询和下载，不决定某条公告是否应进入分析。`Announcement` 保存统一字段，同时用 `source_metadata` 容纳网站特有字段。这样既能保留原始语义，又避免后续代码依赖某个网站的字段名。

巨潮适配器记录请求时间、参数、HTTP 状态和返回文本，默认访问间隔为一秒，仅访问公开网页接口。

### 分类层

分类器使用末尾对齐的白名单语法识别完整年度报告。仅凭标题含有“年度报告”不足以判断正文，因为业绩说明会、摘要和更正公告也可能包含同一短语。

分类结果不只有真假值，还包含摘要、英文版、H股版、取消、说明公告和版本标记。错误分析因此可以定位到具体规则，而不是只看到“未找到”。

### 版本层

版本判断先取符合完整报告规则的公告，再按发布日期处理。最新日期只有一份时采用该份；同日存在多份时，只有唯一一份明确标注为修订、更正或更新才会自动采用。其余情形返回 `ambiguous`。

无法根据公告日期和版本标记完成选择时，结果记为 `ambiguous`，供后续确认。

### 文件层

下载内容经过四项处理：

1. 检查PDF文件头；
2. 检查文件大小下限；
3. 尝试读取页数；
4. 计算SHA-256。

通过检查的文件使用同目录临时文件写入，完成后再由操作系统原子替换。清单同时保存来源地址、公告编号、文件路径、字节数、页数和校验值。

### 章节层

章节定位以页为单位查找标题行，内置业务概况、核心竞争力和研发投入的常见写法。返回值包含章节名、匹配写法、页码和原始行。

章节定位返回标题匹配文本和候选页码。PDF 文本顺序、目录页、跨行标题和扫描质量可能影响结果，正文范围可结合版面分析继续确定。

## 结果文件

`records.jsonl` 每行对应一家发行人，包含：

- 检索时间和来源；
- 所有返回公告及其分类；
- 版本判断和每条公告状态；
- 最终文件的来源地址；
- PDF检查结果；
- 失败类型和错误信息。

JSONL适合增量读取，也方便导入DuckDB、SQLite、Polars或Pandas。项目不绑定数据库，以减少在小规模使用中的配置成本。

## 测试策略

自动测试不访问网络。标题样例覆盖正文、摘要、英文版、H股版、说明公告和修订版本；版本样例覆盖唯一正文、日期更新、同日明确版本和同日冲突；PDF由测试代码在内存中生成；章节定位使用合成页文本；来源适配器使用模拟会话。

网络接口可用性通过少量证券代码单独检查。

## 扩展接口

- `DisclosureSource` 用于接入新的公告来源；
- `classify_annual_report_title` 集中管理标题规则；
- `select_current_version` 处理公告版本关系；
- `validate_pdf_bytes` 接收可配置的文件大小下限；
- `locate_sections` 接收自定义章节名称和标题写法。
